## Scope

This update applies prospectively across nightfall!punk's living ledgers and development conversations. It does not rewrite immutable archive branches or falsify what earlier ledgers recorded at the time.

## Governing method

Use the dialectic:

`ZERO FAMILIARITY -> MAXIMAL FAMILIARITY -> ACTUAL PROJECT STATE -> NEGATION -> SYNTHESIS -> PRAXIS -> REVISION`

Shorthand: `DEP:0-INF-A-N-S`.

The method treats zero genre familiarity and total genre familiarity as counterfactual inquiry poles, not literal claims about designer or assistant knowledge. Actual development always operates from bounded, corrigible knowledge.

## Cross-ledger status vocabulary

Important claims should be distinguishable as:

- `OBSERVED`
- `IMPLEMENTED`
- `DESIGN COMMITMENT`
- `WORKING HYPOTHESIS`
- `ANALOGY/PRECEDENT`
- `ASPIRATION`
- `OPEN QUESTION`

Hard invariants:

- `ASPIRATION != IMPLEMENTATION`
- `ANALOGY != EVIDENCE`
- `DESIGN COMMITMENT != OBSERVATION`
- `COHERENT PROSE != PROOF`

## Master design ledger

Apply the method to all future design synthesis. Genre familiarity supplies precedent but cannot dictate the solution; zero-familiarity inquiry may suspend convention but cannot erase accumulated practice. Project identity should be triangulated through both similarity and difference.

For major new design propositions, record the smallest testable synthesis rather than promoting the broad conceptual framing directly into project truth.

## Architecture / engineering ledger

Architecture must distinguish current wired ownership/data paths from desired future structure. The implementation/proof path is authoritative over architectural rhetoric when they conflict.

Dependency invalidation applies: when a premise changes, downstream architectural inferences must be rechecked rather than textually renamed.

## AI / social ecology ledger

Preserve the existing epistemic separation:

`server truth != actor knowledge != group report`

Add the development-side analogue:

`project reality != conversational model != comparative analogy`

The AI architecture's bounded knowledge becomes a methodological mirror for development itself: both actors and developers operate on partial evidence and revise models through consequences.

## Compare-5 / research ledger

Compare-5 now explicitly inherits `DEP:0-INF-A-N-S`.

Every important comparison asks:

1. What is the underlying problem without genre assumptions?
2. What has the genre/subgenre already learned?
3. What does nightfall actually implement?
4. What could be wrong in the comparison or novelty claim?
5. What is the smallest testable delta?

Require both similarity and difference. Similarity-only risks imitation; difference-only risks novelty theater.

## Philosophy / PRAXIS ledger

Theory is not an implementation claim. Philosophical, Marxian, ecological, evolutionary, phenomenological and game-theoretic concepts may enter code only through bounded material relations that can become an affordance, consequence, trace, constraint, incentive or cause.

Preferred translation chain:

`THEORY -> RELATION -> MECHANISM -> BOUNDED STATE -> C/PSEUDOCODE -> TEST -> OBSERVATION -> REVISED THEORY`

## STEWARD / ledger discipline

STEWARD should preserve uncertainty rather than normalize it away. When consolidating discussions:

- keep hypotheses labeled as hypotheses;
- retain unresolved contradictions as open questions;
- identify dependent claims when a premise is corrected;
- do not silently promote aspiration to implementation;
- prefer concise cross-references over duplicated doctrine;
- keep archive ledgers immutable.

## SIGNAL / communication discipline

SIGNAL should communicate project claims according to their epistemic status. Public-facing language may describe ambitions clearly but must not imply that an unproven feature is already implemented.

Recommended distinction:

- "we are building / exploring" = aspiration or active design;
- "the current build implements" = implementation claim;
- "testing suggests / the video shows" = observed evidence;
- "inspired by / comparable to" = analogy, not equivalence.

## Business Model Philosophy & Community Ledger

Apply the same method to Red Hat, id Software/id Tech, copyleft commercialization, producer cooperatives, triple-bottom-line practice, infra-infrastructure and community development.

Business precedents are comparator models, not templates. For each precedent distinguish:

`TRANSFERABLE MECHANISM / HISTORICAL CONDITION / NIGHTFALL EQUIVALENT / GAP / RISK / SMALLEST EXPERIMENT`

Mission aspirations, organizational commitments, tested community practices and actual financial evidence must remain separate statuses.

## Build readiness / acceptance

Before accepting a build or major contract, audit for **status drift** and **dependency drift**.

Acceptance blockers include:

- aspiration recorded as implementation;
- analogy recorded as fact;
- design intent recorded as observed behavior;
- old premise with unrevised descendants;
- comparison whose source identity/meaning was corrected but whose dependent conclusions were not rerun;
- architecture prose contradicted by code/test/video without reconciliation.

The build/video/test loop remains the final corrective mechanism:

`PROMPT -> CONCEPT -> SPEC -> CODE -> BUILD -> PLAY/TEST -> OBSERVATION -> PROMPT'`

## Canonical maxims

> Never allow familiarity to foreclose inquiry, and never allow unfamiliarity to erase accumulated knowledge.

> The strongest precedent is a question, not an authority.

> The current build is allowed to embarrass the current theory.

> A correction should invalidate dependent assumptions, not merely its spelling.

> Good development produces better ignorance as well as better knowledge.
