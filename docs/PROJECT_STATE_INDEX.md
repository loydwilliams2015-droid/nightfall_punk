## Retrieval order

When answering any question about current/future build identity, scope, handoff, or accepted design state, consult in this order:

1. **PROJECT_STATE_INDEX.md** — version identity and current canonical mapping.
2. Newer explicit user correction recorded in the index.
3. Current branch / PR / exact-head evidence.
4. Current version handoff/readiness ledger.
5. Specialist ledgers (AI, architecture, Compare-5, pace, brand, etc.).
6. Library/chat artifacts as ancestry or exploratory evidence only.

A branch name or old planning filename may lag the roadmap. It is evidence of development history, not automatic authority over current version identity.

## Status vocabulary

- **NEXT** — reserved next major build identity.
- **CANONICAL DESIGN** — accepted scope or method.
- **PLANNING ANCESTRY** — useful earlier analysis, but not authoritative for version naming.
- **EXPLORATORY** — unresolved research or hypothesis.
- **ARCHIVE** — immutable accepted historical state.

## Naming correction rule

A planning file or branch name does **not** establish complete canonical version identity by itself.

Canonical version identity requires one of:
- explicit user designation;
- a recorded correction in this index;
- active branch/PR identity accepted as current;
- a frozen handoff/readiness contract.

If these disagree, do not silently reinterpret. Record the conflict and use the newest explicit correction while preserving historical artifacts as evidence of development history.

## Handoff rule

Every major version transition should record:

`FROM -> ACCEPTED PROOFS -> OPEN GAPS -> TO -> NON-GOALS -> PAC-MAN ADVANCEMENT BENCHMARK -> HUMAN GATE`

The Pac-Man benchmark is a recurring comparative diagnostic for major builds, not a substitute for executable CI or human play evidence.

## Memory discipline

1. Never answer a version-scope question from conversational memory alone when the repo/index can be checked.
2. Never infer missing version numbers.
3. Distinguish **implementation**, **design commitment**, **planning ancestry**, and **aspiration**.
4. When the user corrects a version mapping, update this index before propagating the correction elsewhere.
5. Historical archive ledgers remain immutable; corrections are prospective and indexed here.
6. Prefer one compact canonical index over duplicating the same version map across many ledgers.
7. Branch names are historical identifiers and may become semantically stale; do not let them override the canonical roadmap.
8. Before a major-build answer, retrieve the relevant version row plus its current handoff and planning artifact.
