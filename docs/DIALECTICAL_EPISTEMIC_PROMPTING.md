# nightfall!punk — Dialectical Epistemic Prompting

Status: **cross-ledger development-method contract**. Applies prospectively to living nightfall!punk research, design, architecture, implementation, comparison, proof and business/community work. Historical accepted/archive ledgers remain immutable records of what was known or believed at their closeout.

## Purpose

nightfall!punk development operates under imperfect knowledge. Conversation must not pretend either complete genre ignorance or complete genre mastery. Instead, both are used as counterfactual inquiry poles that discipline the actual situated state of the project.

> **Never allow familiarity to foreclose inquiry, and never allow unfamiliarity to erase accumulated knowledge.**

The method is **Dialectical Epistemic Prompting**: zero familiarity <-> maximal familiarity -> situated praxis -> revision.

## Five-stage query protocol

For consequential design or development questions, use:

`0 -> infinity -> ACTUAL -> NEGATION -> SYNTHESIS`

1. **ZERO FAMILIARITY / NAIF** — suspend inherited genre answers. What problem exists if FPS/subgenre conventions are temporarily bracketed?
2. **MAXIMAL FAMILIARITY / ARCHIVIST** — reconstruct the strongest available precedent: genre history, alternatives, known tradeoffs, failures and neighboring mechanisms.
3. **ACTUAL / ENGINEER** — identify what nightfall!punk currently implements, proves, observes or merely intends.
4. **NEGATION / CRITIC** — ask what premise, analogy, name, interpretation, dependency or supposedly novel claim could be wrong.
5. **SYNTHESIS** — choose the smallest coherent next proposition or implementation consequence that survives the comparison and is testable.

The synthesis is a working model, not final truth.

## Four conversational roles

- **NAIF:** what would we ask without genre assumptions?
- **ARCHIVIST:** what has the genre/subgenre already learned?
- **ENGINEER:** what does the present code/build actually do?
- **CRITIC:** what if the coherent story is nevertheless wrong?

No role has sovereignty. The Engineer is constrained by artifacts; the Archivist cannot convert precedent into obligation; the Naif cannot erase accumulated practice; the Critic must produce a falsifiable objection rather than generalized skepticism.

## Epistemic status tags

Every important ledger claim should be legible as one of:

- **OBSERVED** — directly seen in build/video/log/test/source evidence.
- **IMPLEMENTED** — present in code or authoritative data path.
- **DESIGN COMMITMENT** — intentionally locked direction, whether or not fully implemented.
- **WORKING HYPOTHESIS** — plausible explanation or proposed relation awaiting evidence.
- **ANALOGY / PRECEDENT** — comparison used to illuminate a mechanism; not proof that nightfall implements it.
- **ASPIRATION** — target quality, feeling, scope or parity goal.
- **OPEN QUESTION** — unresolved uncertainty deliberately preserved.

Hard rule:

> **Aspiration != implementation. Analogy != evidence. Coherent prose != proof.**

## Dependency invalidation rule

When a material premise is corrected, all dependent inferences become candidates for re-evaluation.

Example:

`premise -> comparison -> design inference -> mechanic/architecture claim`

If the premise changes, do not perform a word substitution and preserve the descendants automatically. Re-run the dependent comparison and mark downstream claims as reaffirmed, revised, deferred or rejected.

This is the conversational analogue of invalidating dependent state after an authoritative truth change.

## Research and comparison rule

Similarity without difference encourages imitation. Difference without similarity encourages novelty theater. For important references ask both:

1. **How are we like this?** — identify inherited or convergent mechanism.
2. **How are we unlike this?** — identify transformed relation, constraint, rejection or project-specific composition.

Project identity is relational:

`identity = inherited functions + transformations + novel relations`

Compare mechanisms, not feature inventories.

## Praxis closure

Conversation does not close the epistemic loop. Artifacts do.

`PROMPT -> CONCEPT -> SPECIFICATION -> C -> BUILD -> PLAY/TEST -> OBSERVATION -> REVISED PROMPT`

The project is the third object capable of correcting both designer and assistant.

Evidence priority for implementation claims:

`authoritative code/data path -> automated proof/log -> human build/video observation -> interpretation -> analogy/aspiration`

A higher layer may motivate inquiry but may not overwrite contradictory lower-layer evidence.

## Better ignorance

Successful development does not merely accumulate confidence. It should increase the precision of uncertainty.

Preferred loop:

`bounded knowledge -> counterfactual ignorance -> comparative expertise -> hypothesis -> praxis -> contradiction -> better ignorance`

A good iteration ends with fewer false certainties and more sharply bounded open questions.

## Cross-ledger application

### Master/design ledger
Record whether a proposition is observed, implemented, committed, hypothetical, comparative, aspirational or open. Avoid promoting an attractive synthesis directly into project truth.

### Architecture/engineering
Separate desired architecture from currently wired ownership/data paths. If code behavior contradicts architectural prose, code/proof wins and the prose must be revised.

### Compare-5/research
Use references as adversarial comparators, not authorities. Require a current equivalent, delta, disposition and smallest testable consequence.

### AI/social ecology/philosophy
Distinguish descriptive world-model claims from normative metaphor and from implementation. Translate theory into bounded mechanisms only when a material relation can become an affordance, consequence, trace or cause.

### Business/community
Treat business analogies such as Red Hat/id/producer-cooperative precedents as models with transferable mechanisms and incompatible conditions, not templates. Separate mission aspiration, organizational commitment, tested practice and financial evidence.

### Build readiness
Before acceptance, audit each headline claim for status drift: `ASPIRATION -> IMPLEMENTED`, `ANALOGY -> FACT`, `DESIGN -> OBSERVED`, or `OLD PREMISE -> UNREVISED DESCENDANT` are acceptance blockers until corrected.

## Standard shorthand

`DEP:0-INF-A-N-S`

Expanded:

`ZERO -> MAX-PRECEDENT -> ACTUAL -> NEGATE -> SYNTHESIZE -> IMPLEMENT/PROVE -> REVISE`

Use the shorthand when a ledger needs to record that a consequential decision passed the full epistemic cycle without repeating this document.

## Maxims

> **The strongest precedent is a question, not an authority.**

> **The current build is allowed to embarrass the current theory.**

> **A correction should invalidate its dependent assumptions, not merely its spelling.**

> **Good development produces better ignorance as well as better knowledge.**
